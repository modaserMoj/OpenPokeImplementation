OpenPoke baseline findings (pre-fix), 2026-10-12
=================================================
Method: real server code, scripted fake LLM, faked Gmail layer, throwaway data dir.
Reproduce: python evals/run_baseline.py   (writes evals/logs/*.txt)
No real LLM or Gmail was used, so latency/cost numbers below are code-path
measurements, not model measurements. Token counts are chars/4 estimates.

Every claim in the earlier write-up was reproduced. Items marked NEW were
found while building the probes.

Not covered by an offline probe (needs a real model): routing accuracy, reply
quality, true cost/latency. Those belong to the eval harness built in the fix phase.

Proposed fix order (all unit-testable on a mocked LLM):
  1. Send guard in code (06)             - safety, small
  2. Roster -> registry w/ metadata, atomic cross-platform writes, lock (01,02,07,08)
  3. Retrieval routing + lifecycle + merge (01,02)
  4. Per-agent compaction, stop truncating tool output blindly (03)
  5. Per-agent serialisation, shared dispatcher with coalescing window (04,05)
  6. Small stuff (09, 10, duplicated request)
  7. Eval harness: simulated 300-agent history, labeled requests, before/after

Found while getting the app running (fixed in place, 2026-10-12)
----------------------------------------------------------------
NEW  HIGH  Gmail connect broken: client.py used connected_accounts.initiate(), which
           Composio retired for managed OAuth configs (400). Fixed: use link().
NEW  MED   No max_tokens on LLM requests -> OpenRouter asks for the 64k model max and
           returns 402 unless the balance covers it. Fixed: default cap 2048
           (OPENPOKE_MAX_TOKENS to override).
NEW  LOW   Interaction-agent failures log only "Interaction agent failed"; the error is in
           logging `extra`, which the log format never prints, so the cause was invisible.
NEW  MED   Active Gmail user id is held only in process memory (client.py
           _ACTIVE_USER_ID). A server restart silently disconnects Gmail while the
           browser still shows "connected" (localStorage). Tools then fail with
           "Gmail not connected".
NEW  MED   When the interaction agent's LLM call fails, the user gets no message at all
           (turn just fails; error only in server log). Seen twice with 402s.
NEW  LOW   Duplicate draft shown to user: send_draft() posts the draft as a chat message,
           then the prompt-mandated send_message_to_user() repeated the full draft again
           (live, 2026-10-13 00:11). Prompt never says "don't repeat the draft"; no code dedupe.
NEW  MED   No retry/backoff on HTTP 429 from the LLM provider: a burst of ~20 calls/min
           made every later call fail (seen in the eval harness; a live turn would just die
           with no message to the user). Harness now retries; product code does not.

Real-model routing baseline (results/baseline/summary.txt, 40 requests, 277-agent history)
-----------------------------------------------------------------------------------------
Routing ACCURACY is already high (95%); the cost of overload shows up elsewhere:
  primary-agent hit rate   25%   threads split over 2-4 agents: 3 of 4 requests land on a
                                 non-primary variant, i.e. context is scattered
  prompt tokens/routing call 6,549 (277 agents; scales linearly with roster size)
  cost/request $0.0227, latency p50 2.9s / p95 4.6s
  indirect requests (by last name/topic, not agent name) 80%: misses are the metadata gap
So the fix targets are: context fragmentation, prompt size/cost, indirect lookup, plus the
safety and reliability findings above. Do NOT claim accuracy gains beyond ~5 points.

Real-model prompt growth (results/cost_scaling_baseline/summary.txt, $0.195, 7 calls)
  main agent, conversation history: 3,340 tok (0 msgs) -> 6,657 (50) -> 9,998 (100): $0.010 -> $0.030/turn
  worker agent, own log:            3,532 tok (0 runs) -> 11,686 (20) -> 23,779 (50): $0.011 -> $0.072/call (6.7x)
  (replaces the earlier fake-tool estimate of ~1k -> 11k tokens in logs/03)
